# 员工分页与 Redis 请求指纹基准复测

日期：2026-11-07。范围：本机独立 Docker 容器、合成数据；未连接正式库。本文只记录本次实测，不把局部数据外推为生产承诺。

## 环境与数据

- Windows 11，i7-14700HX（28 逻辑处理器），16 GB 主机内存；Docker Desktop / WSL2。
- MySQL 8.0.46、Redis 7.4.12、Java 17.0.17。
- 10,000 / 50,000 / 100,000 条合成员工，另加 1 个 superadmin；每轮新建 MySQL 容器后导入 `db.sql`，插入完成后执行 `ANALYZE TABLE`。
- 每个规模、场景先做 2 次不记录预热，再记录 7 次取中位数；奇偶轮交替执行历史/当前变体。
- 分页样本逐条断言历史与当前的 `total` 和返回 ID 顺序完全一致；不一致时基准直接失败。

## 员工分页

历史实现为查出全部员工与管理员、在 Java 内存中合并排序后分页；当前实现为数据库 `UNION ALL` 过滤、排序和分页。

| 规模 | 场景 | 历史内存分页 | 当前数据库分页 | 提升 | 历史线程分配 | 当前线程分配 |
|---:|---|---:|---:|---:|---:|---:|
| 10k | first | 153.05 ms | 17.29 ms | 8.9x | 161.94 MB | 0.16 MB |
| 10k | deep | 151.47 ms | 18.99 ms | 8.0x | 161.94 MB | 0.16 MB |
| 10k | filtered | 16.93 ms | 10.72 ms | 1.6x | 9.17 MB | 0.18 MB |
| 50k | first | 730.26 ms | 117.27 ms | 6.2x | 813.03 MB | 0.16 MB |
| 50k | deep | 719.89 ms | 127.52 ms | 5.6x | 813.03 MB | 0.16 MB |
| 50k | filtered | 50.25 ms | 69.92 ms | **0.72x（当前慢）** | 9.17 MB | 0.18 MB |
| 100k | first | 1429.85 ms | 240.89 ms | 5.9x | 1624.45 MB | 0.16 MB |
| 100k | deep | 1399.88 ms | 256.72 ms | 5.5x | 1624.45 MB | 0.16 MB |
| 100k | filtered | 156.74 ms | 140.24 ms | 1.1x | 89.87 MB | 0.18 MB |

- first/deep 的历史分页每次执行 6 条 SQL，返回 20,004 / 100,004 / 200,004 行；当前固定 2 条 SQL、返回 21 行。
- 10k first 的历史完整 `page()` 为 8,348.9 ms、10,008 条 SQL、750.72 MB；当前为 17.29 ms、2 条 SQL、0.16 MB。历史完整路径包含每次 GET 都执行的档案同步（约 1 万次 `selectById`），不能全部归功于分页；当前已把该修补移出查询路径，改为显式维护方法。
- 50k filtered 当前比历史内存分页慢约 19.7 ms：当前仍要扫描 `dept_id` 索引的 5 万行再做 UNION/排序，而历史实现在这个规模只物化 1,114 行。100k filtered 时历史要物化 11,114 行，当前反而略快。没有为此继续加索引或重写 SQL。

## COUNT SQL

旧 SQL 是 `COUNT(*)` 套在 `UNION ALL` 物化结果外，会先完成普通员工与管理员合并、join 后再计数。当前拆成两个子查询：员工表按 `is_deleted` 覆盖索引计数，管理员表单独计数。

| 规模 | 场景 | 旧 count | 新 count | 提升 |
|---:|---|---:|---:|---:|
| 10k | first | 19.0 ms | 0.99 ms | 19x |
| 10k | deep | 17.5 ms | 0.93 ms | 19x |
| 10k | filtered | 7.44 ms | 2.91 ms | 2.6x |
| 50k | first | 144 ms | 4.87 ms | 30x |
| 50k | deep | 136 ms | 4.90 ms | 28x |
| 50k | filtered | 37.7 ms | 27.3 ms | 1.4x |
| 100k | first | 266 ms | 9.36 ms | 28x |
| 100k | deep | 290 ms | 11.5 ms | 25x |
| 100k | filtered | 77.5 ms | 54.5 ms | 1.4x |

同一批 `EXPLAIN ANALYZE` 中分页 SQL 本身的 actual time 基本不变（100k first 约 263→290 ms、deep 296→312 ms，属于运行间波动）。无过滤/深分页的请求提升主要来自 count；filtered 的 count 仍受 `dept_id` 索引扫描限制。

## Redis 请求指纹

同一基准、同一组参数（Map + null + int[]）、同一 Redis 7.4.12：

| 指标 | 优化前（每次新建 mapper） | 优化后（静态复用） | 变化 |
|---|---:|---:|---:|
| 100 次指纹 | 73.71 ms | 1.46 ms | 50.5x |
| 单次指纹 | 737 µs | 14.6 µs | 50.5x |
| 100 次线程分配 | 21.9 MB | 430.5 KB | 50.9x |
| 单次线程分配 | 224,258 B | 4,408 B | 50.9x |

两次样本的指纹值完全相同：`7c0965c90c6c199264cc5e810f163bbbd3276f6410c6613ad456b6433f4fa0c1`。复用 `ObjectMapper` 没有改变 Map 排序、null/数组边界和 SHA-256 结果，只去掉了每次调用新建 mapper 的初始化和分配。

真实 AOP + Redis 竞争路径（每轮 10 次记录，batch 中位数）：

| 并发 | 优化前 | 优化后 | 提升 |
|---:|---:|---:|---:|
| 1 | 4.80 ms | 1.30 ms | 3.7x |
| 10 | 6.49 ms | 2.24 ms | 2.9x |
| 50 | 19.65 ms | 5.03 ms | 3.9x |
| 100 | 34.90 ms | 6.54 ms | 5.3x |

每轮均为 1 次实际执行、N-1 次拒绝；防重语义未变。这里测的是单实例、同参数竞争下的批次耗时，不是吞吐上限或跨实例压测。

## 回归与边界

- 完整本地回归 44 项通过，0 失败、0 错误、0 跳过。
- 覆盖：员工/管理员合并、`empName`/`status`/`deptId` 过滤、负 ID 只读管理员、逻辑删除行排除、count 与分页行数一致、系统管理部筛选、真实 Sa-Token 401/403/200、`page()` 只读、安全/库存既有回归。
- 合成数据、单机 Docker，不能据此承诺生产绝对延迟。
- `page()` 仍是 count + 分页两条查询，并发写入时 total 与当前页不是固定快照（原有边界）。
- 分页 SQL 仍会物化 `UNION ALL` 结果后排序；50k filtered 当前慢约 19.7 ms，已在表中保留。
- 历史 `page()` 的档案同步已移出 GET；如果存在没有员工档案的历史 `employee` 账号，需要显式调用维护方法才会补档。
- Redis 只测当前实例的指纹与本地防重路径；故障切换窗口、跨实例幂等边界以 `docs/redis-acceptance.md` 为准。
