# 库存并发与事务：第一项修复

## 问题与实际改动
SalesService.delete 原先先增加库存，再 deleteById，且不检查删除影响行数。两个请求都读到正常销售单时，后来的删除可能影响零行，却已经恢复库存。
现在先用 id、bizStatus=1 条件执行逻辑删除；MyBatis-Plus 补充未删除条件。仅影响一行才增加库存，失败抛 BusinessException。原有 @Transactional 保留。文件：SalesService.java、SalesDeleteTest.java；环境修复另涉及 back/mvnw.cmd。

## 请求链路
销售删除 Controller → 权限校验 → SalesService.delete → 查询单据及当天限制 → 条件逻辑删除 → 检查影响行数 → 原子增加商品库存 → 提交事务。异常沿统一异常处理返回。事务应使删除和库存修改一起提交或回滚，真实数据库回滚仍待验证。

## 原理与选择
超卖是已接受的销售数量超过可用库存。现有 decreaseStock 使用 stock >= quantity 条件和 stock = stock - quantity，在同一 UPDATE 中判断和扣减，不应替换成 Java 先查再赋值。数据库事务把订单与库存写入作为一个提交单位；后续写入失败需要回滚此前写入，避免有订单没扣库存或已删订单没恢复库存。
条件逻辑删除也是竞争入口：两个请求不能都把同一未删除正常单据变成已删除。受影响行数为一才取得本次操作资格；零行意味着状态已变化。Redis 短时间防重不能代替这个规则。

## 验证边界
SalesDeleteTest 模拟读完单据后另一事务已处理该行，要求当前调用抛业务异常且不调用库存 Mapper。修复前已实际失败。它不是真实并发实验，也不证明事务回滚。
真实 MySQL 后续应以屏障同步两个事务读取同一订单，检查只成功一次、库存只加一次；再注入库存更新异常，检查逻辑删除回滚。超卖测试用固定初始库存和多线程销售，断言成功销售总量、最终库存、业务记录相互一致，不以执行速度作为结论。

## 面试问答
1. 为什么事务不能自动防重复删除？事务保证原子提交，但两个事务仍可先后执行重复业务；必须检查状态转换结果。
2. 为什么不加 synchronized？数据库条件更新能覆盖多个应用实例，Java 进程锁覆盖不了。
3. 为什么不能先恢复库存？若删除竞争失败且未检查行数，事务仍可能正常提交库存变化。
4. 影响行数为零为什么报错？当前请求未取得状态转换资格，不应继续库存副作用。
5. 单元测试通过是否证明并发安全？不能；需真实 MySQL 隔离级别、逻辑删除 SQL、事务代理与竞争调度验证。
6. 为什么需要回滚？删除成功后库存更新失败，必须撤销本事务的删除，否则单据与库存不一致。

## 退货并发与来源保护实际进展
采购退货、销售退货现在使用 SELECT ... FOR UPDATE 锁住来源单据，并对有效退货集合使用当前读。原因：仅等待来源锁但继续普通快照读，在 REPEATABLE READ 下可能仍看到旧退货额度。锁随 Service 事务结束释放，不引入 Java 全局锁。
采购、销售删除及作废前锁定同一来源行，并拒绝存在有效退货的单据。保守规则为先撤销有效退货，再撤销来源；不会自动改写历史记录。
真实 MySQL 新增两项并发退货测试：4 线程各退 2 件，来源 5 件，成功 2 次、有效退货总量 4；采购退货库存 10→6，销售退货库存 10→14。
最终一次本轮测试集合：13 项，失败 0，错误 0，跳过 0。包括 5 项销售/退货 MySQL 集成测试、2 项采购 MySQL 集成测试、4 项删除单元测试、2 项采购单元测试。重复执行不重复计数。
