# Redis 防重复提交（开发中）

原项目已使用 PreventDuplicateSubmitAspect 的 @Before 切面、StringRedisTemplate.setIfAbsent(key,"1",TTL,MILLISECONDS) 与本地降级。本轮没有新增Redis框架或改库存事务。

修改：参数从toString拼接改为JSON数组序列化后SHA-256，避免分隔符歧义并隐藏直接参数；Map键排序。用户身份、方法和URI仍参与Key。空值保留。无法序列化时拒绝请求，不悄悄跳过防重。文件参数兼容性尚未验收。
本地表保存绝对过期时间，每次降级清理过期项；同步检查并插入，达到10000个未过期标记时拒绝新请求，避免无限增长。不删除仍有效窗口为新请求腾空间。正常Redis路径仍使用原有原子SET NX+TTL。

真实验证：独立127.0.0.1:16379，使用本机既有Redis5.0.14.1可执行程序，无持久化，不操作默认端口或FLUSH命令。真实AOP代理目标方法用AtomicInteger记录执行次数：首次通过、重复拒绝、不同参数通过、过期重试、8线程相同请求只增加一次执行计数。另一个测试验证无RedisTemplate时本地窗口及过期。
最后统一35项通过（Redis2，员工17，库存16），失败/错误/跳过0。首轮测试因缺少MessageService测试依赖启动失败，补齐后统一重跑通过。

限制：尚未验证不同登录用户、真实连接中断/恢复、容量上限和不同TTL混合场景。无模板降级不等于真实连接失败测试。Redis与本地窗口切换可能额外放行一次；本地记录不跨实例共享。业务失败标记仍保留至TTL，不是真正幂等。
面试：为什么原子设置TTL？避免写Key后进程崩溃留下永久标记。为何数据库约束仍必需？TTL外新请求可再次进入，不同单据ID不受防重约束。为什么本地不能保证多实例？进程内Map不共享。如何判断测试有效？断言代理目标实际调用次数，不能只看Redis存在Key。
运行入口 RedisDuplicateIntegrationTest，需启动独立16379测试实例和显式配置既有MySQL测试环境（复用测试Spring上下文）。本轮仍未验收。

## 用户隔离及边界补充
完整Key（身份、方法、路径、参数摘要）再次SHA-256，避免Redis Key直接暴露用户ID、IP和路径；哈希不是加密，不承诺防字典猜测。
通过真实Sa-Token会话验证同用户同请求拒绝、不同用户与不同接口允许。首次运行测试因未提供Mock响应对象导致登录写Cookie失败，补齐测试响应后统一重跑通过。
文件上传入口未使用防重注解。对直接MultipartFile只取字段名、文件名、类型、大小作为指纹，不读取文件内容；相同元数据的不同内容仍可能冲突，不宣称文件内容幂等。数组、null、Map及分隔符边界测试通过，复杂任意对象不承诺全部支持。
本地混合过期清理和10000条容量边界测试通过：过期记录清除，有效记录不误删，满容量拒绝新业务，空出一个槽位后正常执行。
最新统一38项通过（Redis5、员工17、库存16），失败/错误/跳过0，不与历史批次累计。
剩余：真实Redis断连恢复、容量高并发、Redis恢复资源清理、防重与MySQL联合故障测试。进程命令行检查被系统权限拒绝，本轮没有贸然终止任何Redis进程。第三项仍未验收。

## 最终验收补充（覆盖前文阶段性未完成状态）
第三项限定范围通过，最后统一40项通过（Redis7、员工17、库存16），失败/错误/跳过0，证据和完整边界见 docs/redis-acceptance.md、docs/verification/redis。
新增 ownedRedisDisconnectRecoveryAndDatabaseFailure：测试自己启动Redis、真实终止、PING失败、本地降级、恢复。用真实MySQL sys_user事务验证写入后异常回滚和恢复时唯一约束兜底。它是最小事务业务，不冒充完整员工Controller端到端。
新增 concurrentFallbackNeverExceedsCapacity：9995条记录+16并发独立请求，只执行5次，容量10000。目标执行次数是验证指标，不是性能结果。
面试追问：Redis恢复后为什么还可能进入业务？因为本地标记不自动迁移，测试确实观测到额外放行，但数据库唯一约束拒绝。数据库回滚后为何立即重试被拒绝？防重切面在业务前写标记，事务只控制MySQL，标记等TTL到期。为何不清空Map腾空间？清掉有效窗口会破坏防重，所以满容量拒绝新请求。
亲自练习：阅读上述两个测试，观察Process对象只管理自己启动的实例；将业务故障开关打开，检查sys_user不存在部分提交；不要对业务Redis执行任何关闭或清库命令。
