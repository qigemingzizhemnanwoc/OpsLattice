## 1. 测试范围

本次覆盖新增采购产生数据库库存流水，以及本次改动可能影响的原有采购行为：

- 正常采购、零库存、最小合法数量、连续采购和不同商品的库存隔离。
- 流水全部字段、来源单据关系、操作人、业务时间与实际创建时间。
- 商品、数量、单价、登录及权限校验。
- 采购单、库存、流水任一写入失败时的整体回滚。
- 同商品并发采购、并发失败隔离、现有重复提交限制。
- 原有采购金额计算、默认进价、列表详情和响应格式。

不测试本次范围外的新增流水能力：删除、作废、红冲、采购退货、销售、销售退货、历史补录、流水查询页面和查询接口。也不将本次测试扩展为完整库存台账验收。

## 2. 执行前提与统一约定

### 2.1 环境与数据

以下均为后续执行前应满足的条件，当前尚未准备或验证：

1. 使用独立 MySQL 测试库，表结构与待验收版本一致；回滚和并发结论不得由 H2 或纯 Mock 结果代替。
2. 明确应用版本、工作区差异、数据库版本、事务隔离级别、应用与数据库时区、部署实例数以及防重使用 Redis 还是本地兜底。
3. 准备有采购权限的测试用户 U1、另一名有采购权限的用户 U2、无采购权限的用户 U3，以及无登录态请求。
4. 准备启用商品 G1（库存 10，默认进价 10.00）、G2（库存 0）、G3（库存 20）、已下架商品 G4，以及默认进价为空的启用商品 G5。商品和用户名称均使用非空测试值。
5. 表中的 G1、U1 等均为符号，执行时替换为真实测试 ID，不直接照抄作为请求值。
6. 各用例独立准备数据，库存、单据、流水的基线不能承接上一用例的变动。清理或恢复仅限本轮专用测试数据，不重建正式库，不运行根目录全量初始化 SQL。
7. 正常用例默认使用 U1、启用商品 G1、数量 5、单价 10.00；未明确变化的条件保持默认。不同用例使用不同采购备注标记，格式为 `psf-本轮标识-TC编号`。
8. 防重复提交用例的两次请求必须保持同一登录用户和完全相同的请求参数，包括备注；其他用例避免被上一请求的防重窗口干扰。

### 2.2 操作入口和取证

- 接口映射为 `POST /business/purchases`；当前实施文档记录上下文为 `/api`，直连完整路径为 `POST /api/business/purchases`。执行前核对环境实际路径。
- 业务校验、权限和防重用例通过 HTTP 入口执行；数据库回滚、并发用例使用真实数据库，调用受 Spring 事务管理的业务入口。
- 单元级故障用例可用 Mock/Spy 检查返回值和异常传播，但不能据此宣称数据库回滚通过。
- 保存脱敏请求、响应体、采购单 ID/单号、数据库前后查询结果。当前接口不返回新建采购 ID，应通过唯一测试备注、商品和操作人查到对应采购单，不使用 `MAX(id)` 猜测。
- 不只看 HTTP 状态；同时检查响应体的业务 `code`、错误含义及三张表实际结果。
- 业务操作结束后用独立连接查询已提交数据。失败用例不得仅通过连接采购单的 JOIN 查流水，否则采购单被回滚时可能漏掉孤立流水。
- 检查新增记录时也核对逻辑删除记录：回滚必须消除本次新增记录，不能用“标记删除”冒充事务回滚。

### 2.3 统一预期定义

表格中的“成功一致”“失败无写入”“全部回滚”具体指：

| 简称 | 必须逐项核对的内容 |
| --- | --- |
| 成功一致 | 接口成功；恰好新增一张采购单和一条关联流水；库存只增加采购数量；流水满足 `afterStock = beforeStock + changeQuantity`；所有流水字段符合第 3 节；采购金额仍为单价乘数量 |
| 失败无写入 | 接口返回校验或权限失败；该请求未新增采购单和流水；商品库存等于基线值；其他测试商品数据不变 |
| 全部回滚 | 写入过程中返回失败或抛出异常；本请求已经写入的采购单、库存和流水变化全部撤销；无孤立流水或逻辑删除残留；其他已提交请求不受影响 |

采购数量和单价以合法值测试成功路径。错误文案遵循现有业务约定，不在本需求中新增特定 HTTP 状态或全局错误格式要求。

## 3. 成功流水的字段核对清单

此表是成功用例的预期检查项，不是执行结果。TC-02 首次完整核对，其他成功用例继续应用。

| 字段 | 预期检查内容 |
| --- | --- |
| `id` | 非空，唯一，实际入库后可查到 |
| `goodsId` | 与来源采购单及本次测试商品一致 |
| `goodsName` | 与采购单保存的商品名称快照一致 |
| `changeQuantity` | 等于本次采购数量，为正数 |
| `beforeStock` | 等于本次变动实际发生前库存 |
| `afterStock` | 等于本次变动实际发生后库存，前后差等于变动数量 |
| `bizType` | 固定为 `purchase` |
| `bizId` | 等于本次新建采购单 ID，不能为其他采购单 ID |
| `bizNo` | 等于本次新建采购单单号 |
| `operatorId` | 等于实际登录用户 ID |
| `operatorName` | 等于实际登录用户姓名快照 |
| `operationTime` | 与来源采购单业务时间一致 |
| `createTime` | 非空，属于本次实际创建时间范围，不被用户指定的历史业务时间替代 |
| `remark` | 固定为“采购入库”，不被采购单的自由备注覆盖 |

时间比较采用实际数据库列精度，并在统一时区下记录操作起止时间；秒级存储应允许相应精度的截断误差。

### 4.3 写入失败与整体回滚

TC-21 至 TC-24 使用真实 MySQL，在测试代码中对指定请求注入故障，正常路径仍委托真实 Mapper。故障只存在于测试环境，不添加生产接口开关，不通过删表等 DDL 制造失败。

不得在测试方法外层加一个自动回滚事务来替代业务事务验证。使用独立连接核对基线、采购单、商品库存和全部新增流水，故障注入结束后恢复。

## 6. 数据核对方式

实施文档已经提供按采购测试备注定位采购单、关联流水和商品库存的 SQL，可在确认真实列名后复用。

每次成功用例至少核对：

1. 按本轮唯一标记定位采购单，确认结果数量，再取得采购 ID。
2. 按 `biz_type='purchase'` 与该 `biz_id` 查询流水，确认恰好一条，并执行全部字段检查。
3. 按商品 ID 查询库存，比较原值、采购数量和最终值。

每次失败用例至少核对：

1. 直接查询采购表，确认本次标记未留下记录，包括被逻辑删除的记录。
2. 直接查询专用测试商品在本次操作中新增的流水，对比事前记录集合；可结合故障注入捕获的采购 ID/单号查询，不能只 JOIN 已不存在的采购单。
3. 对比商品库存和其他测试商品基线，确认没有部分写入。

测试环境无人并发操作时可以对比专用商品的完整记录集合；并发用例按每个任务的来源单号和预设标记分别取证。不要用全库总行数替代具体业务核对。
