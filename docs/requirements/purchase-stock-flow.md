# 新增采购生成库存流水

- 版本：v1.0
- 日期：2026-10-23
- 用途：作为本次开发和验收依据；本文不代表功能已实现或测试已通过。

## 1. 背景与目标

系统创建采购单时会增加商品库存，需要同时记录该次库存变动，以便追溯库存为什么增加、增加多少、由谁操作以及来源采购单。

本次目标：每成功创建一张采购单，自动向数据库保存一条对应的采购入库流水。采购单、商品库存与库存流水必须保持一致。

## 2. 需求范围

### 2.1 本次包含

- 沿用现有新增采购入口，由系统自动生成库存流水，无需用户额外操作。
- 记录库存变动数量、变动前后库存及来源采购单等信息。
- 将流水持久化到 `biz_stock_flow` 表。
- 保证采购单保存、库存增加和流水保存全部成功或全部回滚。
- 通过数据库核对业务结果，不新增库存流水页面或查询接口。

### 2.2 本次不包含

- 采购删除、作废、红冲、采购退货的库存流水。
- 销售、销售退货及其他库存变动的流水。
- 历史采购单的流水补录。
- 库存流水查询页面、查询接口、导出、编辑或删除功能。
- 新增采购审批、仓库收货或多商品采购单流程。
- 新增跨请求的业务幂等机制；现有重复提交限制保持原有规则。

由于其他库存变动暂未纳入，本次流水只能追溯新增采购造成的库存增加，不能作为覆盖所有库存变动的完整台账。

## 3. 业务规则

### 3.1 触发条件与权限

- 触发入口为现有新增采购接口 `POST /business/purchases`。
- 沿用现有采购权限和业务校验，包括商品存在且启用、数量为正整数、单价合法等，不扩大操作权限。
- 校验通过并完成采购入库时，自动生成流水。
- 当前采购单对应一个商品，因此每张成功创建的采购单对应一条新增采购流水。

### 3.2 库存与数量

- 流水的变动数量等于采购数量，采购入库记为正数。
- 变动前库存为本次入库实际发生前的商品库存。
- 变动后库存为本次入库实际发生后的商品库存。
- 必须满足：`变动后库存 = 变动前库存 + 变动数量`。
- 多笔采购并发修改同一商品时，不能丢失库存增量；各条流水必须反映各自实际发生的库存变动，不得使用过期库存值形成错误记录。

### 3.3 来源与记录内容

- 流水必须关联本次新建采购单的 ID 和单号，不得关联其他采购单。
- 商品及操作人信息由服务端读取，不由客户端指定流水内容。
- 商品名称、操作人姓名保存为业务发生时的快照。
- 本文沿用现有字段约定：业务类型 `bizType` 为 `purchase`，表示采购入库；备注为“采购入库”。
- 业务时间 `operationTime` 与来源采购单一致：采购单传入业务时间时沿用该时间，否则使用创建采购单时的服务端时间。
- 记录创建时间 `createTime` 表示流水实际创建的服务端时间，不以用户填写的业务时间替代。

### 3.4 原子性与失败处理

- 采购单保存、商品库存增加和库存流水保存必须处于同一个事务中。
- 只有三项操作全部成功，新增采购接口才返回成功。
- 任一步写入失败，接口必须返回失败，并回滚本次操作已经产生的采购单、库存和流水变更。
- 权限或参数校验失败时，不产生采购单，不增加库存，也不产生流水。
- 不允许忽略流水保存失败后仍返回采购成功。
- 被现有重复提交机制拒绝的请求不得增加库存或生成流水。
- “每单一条流水”约束针对同一采购单；不同请求若按现有规则成功创建了不同采购单，则分别产生各自的流水。本次不增加识别这些请求是否属于同一次业务采购的能力。

## 4. 流水数据要求

以下使用现有实体属性名描述数据含义，实际数据库列名、类型和默认值须在实现时核对。

| 属性 | 含义 | 取值要求 |
| --- | --- | --- |
| `id` | 流水唯一标识 | 数据库主键，唯一且非空 |
| `goodsId` | 商品 ID | 与采购单商品一致 |
| `goodsName` | 商品名称 | 与本次采购保存的商品名称一致 |
| `changeQuantity` | 库存变动数量 | 等于采购数量，为正整数 |
| `beforeStock` | 变动前库存 | 本次入库实际发生前的库存 |
| `afterStock` | 变动后库存 | 等于变动前库存加采购数量 |
| `bizType` | 来源业务类型 | 固定为 `purchase` |
| `bizId` | 来源业务单 ID | 本次新建采购单 ID |
| `bizNo` | 来源业务单号 | 本次新建采购单号 |
| `operatorId` | 操作人 ID | 本次登录用户 ID |
| `operatorName` | 操作人姓名 | 本次登录用户姓名快照 |
| `operationTime` | 业务时间 | 与来源采购单业务时间一致 |
| `createTime` | 流水创建时间 | 服务端实际创建时间 |
| `remark` | 流水备注 | 固定为“采购入库” |

上述字段均应保存有效值。采购单自身的备注仍按现有规则保存，不替代流水的固定业务备注。

## 5. 验收标准

以下均为待执行的验收场景，不代表已经测试通过。验收应在独立测试环境或使用明确授权的测试数据进行。

| 编号 | 场景与前提 | 预期结果 |
| --- | --- | --- |
| AC-01 | 有权限的用户对启用商品新增采购，原库存 10，数量 5，单价合法 | 接口成功；新增一张采购单；库存变成 15；新增一条流水，记录 `10 / +5 / 15` |
| AC-02 | 核对 AC-01 的采购单与流水 | 商品、采购数量、来源单 ID、单号、操作人和业务时间一致；业务类型为 `purchase`；备注为“采购入库”；流水主键和创建时间有效 |
| AC-03 | 商品原库存为 0，合法采购 3 | 库存变成 3，流水记录 `0 / +3 / 3` |
| AC-04 | 分别使用不存在商品、已下架商品、空数量、零数量、负数量或非法单价创建采购 | 接口失败；无新增采购单或流水；库存不变 |
| AC-05 | 无采购权限的用户提交新增采购 | 请求被拒绝；无新增采购单或流水；库存不变 |
| AC-06 | 在隔离测试中分别使采购单保存、库存更新、流水保存发生失败 | 每个场景均返回失败；本次采购单、库存和流水变更全部回滚；尤其须验证流水保存失败时，采购单及库存也已恢复 |
| AC-07 | 同一商品原库存 10，依次成功采购 5 和 3 | 最终库存 18；两张采购单各对应一条流水，分别为 `10 / +5 / 15` 和 `15 / +3 / 18` |
| AC-08 | 同一商品原库存 10，无其他库存操作，并发成功采购 5 和 3 | 最终库存 18；两张采购单、两条流水；流水根据实际执行顺序为 `10 / +5 / 15` 与 `15 / +3 / 18`，或 `10 / +3 / 13` 与 `13 / +5 / 18` |
| AC-09 | 请求触发现有重复提交限制 | 被拒绝的请求不额外生成采购单、增加库存或生成流水 |
| AC-10 | 分别传入合法业务时间和省略业务时间创建采购 | 流水业务时间与各自采购单一致；省略时采用服务端时间；流水创建时间均记录实际创建时间 |

验收应保留接口结果和数据库核对结果，并能够通过来源采购单 ID 定位对应流水。仅看到接口成功或代码中的事务注解，不视为一致性与回滚验收通过。
