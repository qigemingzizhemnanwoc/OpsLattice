## 2. 建议方案

### 2.1 处理 Maven 依赖

使用已安装的 Java 17 和 Maven 3.9.12，允许 Maven 联网解析项目原有依赖，然后重跑同一检查命令。保持 `pom.xml` 中的版本不变，不更换镜像、不关闭证书校验、不升级框架。

若网络、仓库或后续编译仍报错，保留原始输出并反馈用户，不跳过错误或自行换方案。

### 2.2 创建独立测试数据库

拟在同一本机 MySQL 实例 `localhost:3306` 创建：

```text
warehouse_management_purchase_test
```

先只读确认该名称是否已存在。如果已存在，先报告其用途与结构，不能覆盖或自动清空。

若名称不存在，先核对现有业务表的字符集、排序规则，再生成只针对新库的建库脚本。数据库名固定写明，脚本中不包含 `DROP DATABASE`，不执行根目录全量 `db.sql`。

该方案采用同实例不同库隔离数据，足以进行本次功能测试；不等同于独立 MySQL 实例或服务器，不用于大规模压力测试。

### 2.3 准备最小表结构

1. 只读提取现有 `base_goods`、`biz_purchase` 和 `biz_stock_flow` 的实际建表定义，不复制业务数据，不复制触发器或存储过程。
2. 检查外键和其他结构依赖；如需额外表或流水表本身不存在，先向用户报告并提供具体增量 SQL，不凭实体字段自动猜测执行。
3. 将已确认结构写入独立增量脚本，目标仅为新测试库；创建前明确列出表名。
4. TC-01 只检查结构，不需要测试采购、用户或商品数据。
5. 后续每轮只准备当前用例需要的虚构商品和用户资料。进入 HTTP 权限测试前，再补充已确认的登录/部门依赖结构，不复制真实用户和密码。

### 2.4 连接与权限

检查程序通过以下本地环境变量接收连接，不回退使用现有应用连接配置：

| 变量 | 拟定值或用途 |
| --- | --- |
| `PURCHASE_TEST_JDBC_URL` | `jdbc:mysql://localhost:3306/warehouse_management_purchase_test` |
| `PURCHASE_TEST_DATABASE` | `warehouse_management_purchase_test`，连接后核对实际库名 |
| `PURCHASE_TEST_USERNAME` | 用户确认的本地数据库账号；建库阶段和业务测试阶段分别核对权限 |

数据库建库和只读结构检查需使用具备相应权限的账号。后续业务测试优先使用权限限定到新库的测试账号；具体账号及授权脚本在检查当前权限后列出给用户确认。

元数据查询还需确认账号能看到相关表、索引和触发器，不能把权限不足造成的不可见当作对象不存在。

## 3. 确认后的执行顺序

1. 联网解析原项目依赖，确认检查程序可以编译；出现新错误立即反馈。
2. 只读核对本机数据库连接、目标库名是否存在、源表结构和权限。
3. 将实际建库建表 SQL 提交用户查看；收到执行确认后，仅创建指定测试库及已列出的表。
4. 设置本进程测试连接变量，运行 TC-01，只读核对结构与事务前提。
5. TC-01 如发现缺表、字段不兼容或触发器需审查，先反馈，不自行改表来让检查通过。
6. 通过前提检查后，按“一条测试 → 运行记录 → 最小功能改动 → 重跑该测试”继续。预期的功能缺口由对应测试暴露；遇到超出既定实施方案的问题先等待用户决定。
