## 1. 目标与边界

通过现有新增采购入口，在保存采购单和增加商品库存的同一事务内，保存一条 `biz_stock_flow` 记录。三项写入全部成功或全部回滚。

本次只涉及新增采购和数据库落库，不新增页面或查询接口，不扩展删除、作废、红冲、退货、销售或历史补录。沿用现有权限、参数校验和重复提交机制。

本文件所在的 `docs/requirements/implementation/` 专门存放落地实施文档；需求文档保留在上一级。

## 3. 目标调用链与最小改动

```text
POST /api/business/purchases
  → PurchaseController.create：参数校验、现有防重复提交
  → PurchaseService.create：进入事务
      → 校验权限、数量、商品和单价，取得登录用户和业务时间
      → 保存采购单，检查影响行数与回填 ID
      → 原子增加商品库存，检查影响行数
      → 读取本次变动后的库存，计算变动前库存
      → 保存一条采购入库流水，检查影响行数

任一环节异常 → 向外抛出 → 事务回滚 → 返回失败
```

## 4. 分步实施

### 第一步：核对真实数据库结构

目的：先确认 Java 对象能正确写入实际表，再修改业务代码。

1. 确认连接的是独立测试库或已获授权的数据库；先只读检查。
2. 执行下列检查并保存结果。若流水表不存在，记录缺失情况，跳过该表的 `SHOW CREATE TABLE`。

```sql
SELECT DATABASE(), VERSION();
SHOW TABLES LIKE 'biz_stock_flow';
SHOW CREATE TABLE base_goods;
SHOW CREATE TABLE biz_purchase;
SHOW CREATE TABLE biz_stock_flow;
SHOW TRIGGERS;
```

3. 核对三张表的存储引擎、商品库存的非空约束、流水字段类型、主键自增、时间默认值，以及是否存在重复扣增库存或自动写流水的触发器。另记录实际事务隔离级别，按数据库版本使用对应的只读查询。
4. 对照需求字段逐项核对。不得因为仓库 SQL 未定义流水表，就认定真实数据库也没有该表。
5. 表已兼容则不改结构；缺失或不兼容时才准备增量建表或变更脚本。

新增表的结构设计基线如下，最终以本步骤核对后的脚本为准：

| 列 | 建议定义 |
| --- | --- |
| `id` | `BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY` |
| `goods_id`、`biz_id`、`operator_id` | `BIGINT NOT NULL` |
| `goods_name` | `VARCHAR(100) NOT NULL`，与现有商品名称容量兼容 |
| `operator_name` | `VARCHAR(50) NOT NULL`，与采购单姓名容量兼容 |
| `change_quantity`、`before_stock`、`after_stock` | `INT NOT NULL`，与现有库存类型兼容 |
| `biz_type` | `VARCHAR(32) NOT NULL`，本次写入 `purchase` |
| `biz_no` | `VARCHAR(30) NOT NULL`，与采购单号容量兼容 |
| `operation_time`、`create_time` | `DATETIME NOT NULL`；按下文明确时间写入策略 |
| `remark` | `VARCHAR(200) NOT NULL` |

新表采用支持事务的 InnoDB，字符集与现有业务表保持兼容。可使用 `(biz_type, biz_id)` 唯一键落实当前“一张来源业务单一条流水”的模型；如果表已存在，必须先核查历史记录和其他写入者是否满足该模型，再决定是否增加约束，不自动清除重复数据。这一约束不等于跨请求业务幂等。

**交付物：**实际表结构核对记录；必要时附增量 SQL 及执行前提。

**完成条件：**需求字段均有正确映射，三张表支持事务，测试数据与正式数据隔离。未达到条件时先解决此步骤，不提交测试采购碰运气。

### 第二步：补齐最小业务改动

1. 保留 `create` 上的 `@Transactional(rollbackFor = Exception.class)`，由 Controller 调用 Spring 管理的 Service。不要在类内绕过代理调用作为事务验证方式。
2. 采购插入影响行数应为 1，且插入后 `purchase.getId()` 非空；否则抛出异常。
3. 保留数据库原子库存自增，更新影响行数应为 1；不使用入口第一次读到的库存进行覆盖写回。
4. 在同一事务内取得更新后库存并生成流水，满足 `beforeStock = afterStock - quantity`。字段取值直接沿用同一采购对象、商品快照与登录用户。
5. `operationTime` 继续使用采购单的业务时间。流水 `createTime` 采用最小明确方案：在保存流水前显式设置服务端当前时间；不为此修改全局时间填充器。若实际表已有默认时间，保持兼容，并核对最终落库值。
6. `bizType` 固定为 `purchase`，`remark` 固定为“采购入库”；采购单自身备注保持原逻辑。
7. 流水插入影响行数应为 1；失败或数据库异常必须向外传播，不能捕获后忽略，也不能将流水写入另一个独立事务。
8. 清理流水 Mapper 的无关价格查询，以及流水实体的无用导入。保留采购 Mapper 中被销售业务调用的方法。

关于并发：现有“先原子更新，再查询库存”不是仅凭源码顺序就能判定的缺陷。本次先保留并使用真实 MySQL 验证。如果测试发现前后库存不连续，先保留执行证据，检查事务、缓存和读取方式；必要时将更新后的库存读取改为同一事务中的显式当前读，例如专用 `SELECT ... FOR UPDATE` 查询，再复测。不要未经证据重构所有库存入口。

**交付物：**采购范围内的代码差异，及每处改动对应的需求条目。

**完成条件：**三项写入均有失败处理，字段完整，原有接口和其他业务路径保持兼容。

### 第三步：验证一笔真实采购落库

使用测试用户、测试商品及合法价格。每次测试使用唯一采购备注标记，例如 `purchase-stock-accept-001`，只用于定位测试采购单，不改变流水固定备注。

1. 记录测试商品 ID、当前库存、相关采购单和流水的基线记录。
2. 原库存为 10 时，通过现有接口采购 5；用测试环境中的真实商品 ID 替换下面的 `123`。

```json
{
  "goodsId": 123,
  "quantity": 5,
  "unitPrice": 10.00,
  "remark": "purchase-stock-accept-001"
}
```

3. 检查响应体 `code` 和业务结果，不能仅看 HTTP 状态。现有成功响应不返回采购单 ID，通过唯一备注、测试商品和操作人定位新采购单。
4. 在确认实际列名后，执行只读核对 SQL。下列查询中的测试标记必须与本次请求一致；不使用 `MAX(id)` 猜测新单据。

```sql
SELECT id, purchase_no, goods_id, goods_name, quantity,
       operator_id, operator_name, operation_time, create_time
FROM biz_purchase
WHERE remark = 'purchase-stock-accept-001';

SELECT f.*
FROM biz_stock_flow f
JOIN biz_purchase p ON f.biz_type = 'purchase' AND f.biz_id = p.id
WHERE p.remark = 'purchase-stock-accept-001';

SELECT g.id, g.stock
FROM base_goods g
JOIN biz_purchase p ON p.goods_id = g.id
WHERE p.remark = 'purchase-stock-accept-001';
```

5. 应为一张采购单、一条流水、库存 15，流水为 `10 / +5 / 15`。同时核对来源单、商品、操作人和两个时间字段。
6. 再执行零库存、连续两次采购、指定业务时间和省略业务时间的场景。时间比较按实际列精度进行，不能因 Java 纳秒与数据库秒精度不同误报失败。

**交付物：**请求参数、脱敏响应、采购单 ID/单号、库存前后值及流水查询结果。

**覆盖：**AC-01、AC-02、AC-03、AC-07、AC-10。

### 第四步：验证失败与回滚

先补充单元测试，再以隔离 MySQL 集成测试验证真实事务。复用 JUnit/Mockito，不以 Mock 的调用次数作为数据库回滚证据。

单元测试至少覆盖：流水关键字段和来源关系、两次插入返回 0、采购 ID 未回填、库存更新失败、流水插入异常向外传播。数量、权限或商品校验失败时应无写入。

集成测试必须调用 Spring 代理下的真实 Service，并使用真实 Mapper 和数据库。可模拟身份来源，但三项数据库写入不能全部替换为 Mock。故障注入仅存在于测试代码中，不为生产接口添加“制造失败”参数。

| 故障注入位置 | 必须验证的结果 |
| --- | --- |
| 采购保存失败 | 无新增采购或流水，库存保持原值 |
| 采购已写入，库存更新失败 | 新采购记录被回滚，无流水，库存保持原值 |
| 采购和库存已写入，流水插入失败 | 采购和库存均回滚，无残留流水 |
| 真实流水已插入，提交前抛出异常 | 三项已发生的写入全部回滚，防止只验证“流水从未写入” |

使用测试专用拦截或 Spy 对指定测试请求注入异常，正常写入仍委托真实 Mapper；测试结束后恢复。请求完成后使用独立数据库连接读取结果。不要依赖测试方法外层自动回滚掩盖 Service 事务失效，也不要在测试中执行建表/删表 DDL 来制造业务失败。

无权限、空/零/负数量、商品不存在或下架、非法单价应通过 HTTP 层补测，以覆盖 DTO 校验和权限链路。保持原有业务错误格式，不在本需求中改造全局异常处理。

**交付物：**故障触发位置、异常结果、独立连接查询的前后数据，以及恢复故障注入的记录。

**覆盖：**AC-04、AC-05、AC-06。

### 第五步：验证并发和现有重复提交限制

并发测试使用隔离 MySQL，每个任务独立事务和连接；不要使用 H2 或纯 Mock 的结果代替 MySQL 并发结论。

1. 准备库存 10 的独立商品，确保没有其他库存操作。
2. 两个任务通过起跑屏障同时发起数量 5 和 3 的采购，各自有独立身份上下文和测试标记，并确认执行存在重叠；不要在已经持有商品锁后设置相互等待的屏障。
3. 两个请求都成功后，从独立连接验证库存为 18、存在两张采购单和两条对应流水。
4. 流水应为 `10 / +5 / 15` 与 `15 / +3 / 18`，或者 `10 / +3 / 13` 与 `13 / +5 / 18`。根据库存前后衔接判断顺序，不用用户可填写的业务时间判断顺序。
5. 若单号冲突、锁超时或其他异常导致只有一个请求成功，记录失败原因；不能将其记为“两笔并发成功”的验收通过。
6. 另行通过 HTTP，在 1800 毫秒窗口内用同一用户提交完全相同请求，确认被防重机制拒绝的请求没有额外写入。此场景保持相同参数，不能用不同备注绕过防重后声称已验证。

现有防重切面按用户、请求路径、方法和参数构造键，优先使用 Redis，不可用时本地兜底。记录测试所用模式及实例数量；一次单实例测试不能证明所有多实例降级情形。窗口外创建不同采购单仍沿用原有行为，不新增业务幂等规则。

**交付物：**并发请求结果、执行重叠证据、两张单据与流水、最终库存、防重拒绝及数据库核对结果。

**覆盖：**AC-08、AC-09。
