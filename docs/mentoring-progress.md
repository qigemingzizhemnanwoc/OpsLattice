## 库存设计核查

- BizStockFlow 实体与 Mapper 存在；PurchaseService.create 已依次插入采购单、增加库存、调用 recordStockFlow，并有 rollbackFor=Exception 的事务注解。私有辅助方法不需要各自再加事务注解；实际回滚尚未验证。
- recordStockFlow 更新后查询库存，以 afterStock - changeQuantity 推算 beforeStock。不能只根据此顺序判断并发错误；应在真实 MySQL 上验证事务、行锁与连续流水。不要改成无保护地先读后覆盖库存。
- 四类业务 Service 的 create/delete/voidDocument 均有事务注解，包括此前被怀疑的 PurchaseReturnService.create。
- 四类业务共 12 个增减库存入口，目前只有采购创建记录流水；审批通过会调用对应 voidDocument。作废并生成红冲单当前只有一次库存反向变化，不能因生成红冲单再重复记一次变更。
- GoodsService.create/update 可直接设置库存，后者存在覆盖并发库存修改的风险，也绕过流水；需明确初始库存与人工调整规则。
- db.sql 没有 biz_stock_flow 建表语句；有 sp_purchase_add_stock 示例过程，未发现 Java 调用。现有操作日志不是包含前后库存的专用库存流水。线上/本地实际数据库是否存在其他机制未核实。
- BizStockFlowMapper 残留从采购 Mapper 复制的 latestValidUnitPrice 查询，与库存流水职责无关。
- 流水 createTime 未显式赋值，需核对真实表默认值和自动填充条件。operationTime 接受业务时间，追溯实际写入顺序不能仅依赖该字段。
- 删除路径先改库存再 deleteById，未检查删除影响行数；并发重复删除有重复反向变更风险。作废路径已有状态条件更新及影响行数检查。
- 来源可退量是原单数量减有效退货数量，不等于当前库存；退货还会检查实际库存。并发退货的来源额度检查缺少锁定，需专项验证，不能用库存非负替代额度约束。
- 防重复提交是短时间窗口，不等于持久化业务幂等。未查验流水表唯一约束，不能宣称防重完整。
- 建议统一一个具体库存服务，集中增减、库存不足检查与流水；保留外层业务事务。先打通采购，再迁移其余入口，不新增框架。
